Technical specification

What the code actually does.

This document is written for reviewers who want to check the architecture, not take it on faith. Every coefficient, gate, weight, and threshold below is transcribed from the running code (assets/js/engine.js, assets/js/data.js, data/*.js, iot-3d.html) — not from an aspirational diagram. Where the implementation is a static snapshot instead of a live feed, or a calibrated constant instead of a literature value, it says so explicitly. Where the code and an earlier draft disagreed, the code is treated as the source of truth and the draft is corrected.

How this was verified: the worked examples in Sections 5 and 6 were produced by actually executing window.FS.engine.listScenarios() / buildPayload() against the shipped data/*.js files under Node (the same code path the browser runs), not hand-derived. 1System overview

FieldShift's MVP is a client-only decision engine: every score, gate, and IDR figure a farmer sees is computed synchronously in the browser from bundled JSON, with one optional live network call (NASA POWER). There is no server, database, or LLM in the scoring path today — Sections 7 and 11 describe the migration target for a production build.

Data layer
data/*.js — five static datasets (crops, field_state, soil, geoglam, calendar, telemetry, bom) plus assets/js/data.js, which adds a demo/live mode switch and overlays a live NASA POWER pull onto agrometeorological_context when available.
Field State
engine.computeFieldState() merges runtime farmer input on top of the documented default field state — the single contract every other module reads (Section 4).
Scenario engine
engine.js — four hard feasibility gates, four weighted sub-scores, a priority-weighted total, and a verdict. Pure, deterministic, synchronous arithmetic — no DOM access, no network call, no LLM call anywhere in this file, by explicit design rule (Section 5).
Economics & confidence
Margin range, break-even price, price sensitivity, and a data-confidence score with human-readable reasons, computed per scenario (Section 6).
Presentation (app.html)
Renders scenario cards, trade-off prose (templated string-building — not LLM-generated), and source-attribution chips. Built and maintained separately from this spec page.
IoT action loop
Physically separate from the web app today: FieldShift Node v1 hardware (Section 8), a firmware state machine (Section 9), and fail-closed safety guardrails (Section 10). Documented as a concept artifact, not yet wired to the scenario engine's output.
Gov/NGO aggregation (optional branch)
Consent-gated, aggregated-only view for extension workers and NGOs (Section 11). Not implemented — there is no backend to aggregate anything yet — documented here as the design target.

2Data sources

The posture is NASA-first: NASA sources anchor the data layer, and every non-NASA source is labelled explicitly, in the UI and in assets/js/data.js's PROVENANCE table. NASA POWER replaced the Open-Meteo-style baseline used in an earlier draft. NASA HLS (30 m) is the documented architecture lead for vegetation trend, with Sentinel-2 L2A (10 m) as the detail layer — see the honesty note below on what is actually wired up. SoilGrids (ISRIC) is explicitly not a NASA source.

3The 48-hour substitution table

Three data layers had an ideal live-architecture design and a different, static reality in the build. This is deliberate engineering judgement under a hard time budget — not a shortcoming being hidden.

Static JSON transcribed once from GEOGLAM Early Warning No.119 (Sept 2026) and the cropmonitortools.org CMET export, baked into data/geoglam.js. GEOGLAM/HarvestGLAM has no stable public API, and its CSV export process queues overnight — incompatible with a 48-hour build cycle.
Soil chemistry Per-request raster sampling against a SoilGrids WCS/REST endpoint for the exact field-polygon centroid, refreshable on demand. One-time point extraction via QGIS "Identify Features" against a downloaded regional GeoTIFF (West Java & Banten), frozen into data/soil.js: pH 6.2, organic carbon 366 dg/kg (3.66%), water retention "Medium". Climate / weather baseline Superseded: an Open-Meteo-style third-party forecast API, as in the earlier draft. NASA POWER, queried live client-side in "Live" mode (see Section 2), falling back silently to the demo snapshot. NASA-first judging criterion, and POWER needs no API key and returns browser-consumable JSON — this is the one row that was successfully wired live, unlike the other two.
Framing: none of these three substitutions were forced by a technical dead end that couldn't be solved — they were the correct call against a 48-hour clock. A live SoilGrids or GEOGLAM integration is a "when we have more time" item, not an "impossible" one; documenting exactly which value is static and why is what keeps this honest.

Source of truth: assets/js/engine.js. Every constant below is copied verbatim from the code, including its inline comment where that comment explains a real calibration or defect-fix decision.

Feasibility gates (hard pass/fail, evaluated before any scoring)

  1. Soil pH. Reject if soil_chemistry.pH falls outside [crop.ph_min, crop.ph_max].
  2. Planting window. Reject if none of the crop's calendar_track entries ever shows "Planting-Early Veg" in the 24-row half-month calendar.
  3. Capital. Reject if capital_requirement_idr_per_ha × area_ha > capital_available_idr_per_ha × area_ha. (Note: because the farmer's capital figure is already expressed per hectare, area_ha cancels out of both sides — the pass/fail outcome is independent of the declared area. A minor code smell, not a scoring bug: the comparison direction is unaffected.)
  4. Water hard-safety-net. Only checked when precipitation_outlook === "Below-average": reject if water_requirement_mm > irrigation.capacity_mm × irrigation.efficiency × 3 (WATER_GATE_MULTIPLIER = 3). Deliberately loose so the ordinary "rice on rainfed under a dry outlook" case is scored poorly, not gated out — matching the calibration target that Scenario A is scored, not marked infeasible.

Sub-score 1 — Water demand suitability

Irrigation table (IRRIGATION):

TypeCapacityEfficiencyRain sensitivity
Rainfed750 mm0.551.00
Furrow1300 mm0.650.50
Sprinkler1500 mm0.780.30
Drip1600 mm0.920.15
  • Precipitation adjustment (PRECIP_ADJ_DELTA, scaled by rain sensitivity): Below-average −0.15, Average 0, Above-average +0.10.
  • NDWI weight: WATER_NDWI_WEIGHT = 0.30 — only a currently-drying reading (NDWI < 0) penalizes; a wet reading gets no bonus.
  • Calibration constant: WATER_K = 110, tuned so Rice under Rainfed + Below-average + NDWI −0.15 (the reference case) lands near 30/100.
  • Blend weights: WATER_IRRIGATION_WEIGHT = 0.6, WATER_ABSOLUTE_WEIGHT = 0.4 — the final score blends the farmer's actual irrigation choice (60%) with the same formula forced to Rainfed (40%, the crop's irrigation-independent exposure to the weather).
raw(crop, irrType) = WATER_K × capacity × efficiency × precipFactor × ndwiFactor ÷ water_requirement_mm score = 0.6 × clamp(raw(actual irrigation)) + 0.4 × clamp(raw(Rainfed)) — the blend that fixes a documented saturation defect: under high-capacity irrigation (e.g. Drip), a pure capacity formula pushed every crop to exactly 100, destroying discrimination between a thirsty crop (rice) and a frugal one (soybean).

Sub-score 2 — Soil health impact

score = 40 + soc_level × soc_preference × 30 + (rotation ? +10 : −13) + (legume following non-legume ? +22 : 0)
  • SOIL_BASE = 40 (neutral start), SOIL_SOC_MAX_BONUS = 30 (soc_level and soc_preference each mapped to {0.3, 0.6, 1.0}).
  • SOIL_ROTATION_BONUS = +10 for breaking the previous crop's cycle; SOIL_MONOCULTURE_PENALTY = −13 for repeating it.
  • SOIL_NITROGEN_FIX_BONUS = +22 when the candidate is a legume following a non-legume.

Sub-score 3 — Climate resilience

score = 100 − 60 × drought_sensitivity × precipRisk − 25 × (1 − heat_tolerance) × tempRisk + (cycle < 90d ? +12 : 0) + GEOGLAM nudge
  • CLIMATE_DROUGHT_WEIGHT = 60, precipRisk = {Below-average: 1, Average: 0.5, Above-average: 0.2}.
  • CLIMATE_HEAT_WEIGHT = 25, tempRisk = {Above-average: 1, Average: 0.5, Below-average: 0.2}.
  • CLIMATE_SHORT_CYCLE_BONUS = +12 for crops with cycle_days < 90 (partial escape from a late-season dry/heat spell).
  • GEOGLAM Early Warning nudge (regional, per-crop): Favourable +3, Poor −8, Failure −15. Only rice and maize have an Early Warning entry in data/geoglam.js — soybean, mung bean, and peanut never receive this nudge (no bonus, no penalty).

Sub-score 4 — Farmer priority alignment

score = 25 + mean(active-priority fits) × 87

Five priorities, each a min-max normalization across the full 5-crop catalogue (rice, maize, soybean, mung bean, peanut — not just the 3 crops offered as MVP scenarios, so mung bean and peanut's presence still shapes e.g. the "Save Water" fit curve even though they are not offered as rotation options):

  • Save Water — inverse-normalized water_requirement_mm.
  • Maximize Yield — normalized base_yield_t_ha.
  • Reduce Climate Risk — normalized (1−drought_sensitivity) + heat_tolerance.
  • Improve Soil Health — normalized nitrogen_fixing + soc_preference.
  • Low Capital — inverse-normalized capital_requirement_idr_per_ha.

PRIORITY_ALIGNMENT_FLOOR = 25, PRIORITY_ALIGNMENT_SCALE = 87. No priorities selected → neutral 50. The mean divides by the actual number of active priorities — a fixed-denominator bug ("DEFECT 1" in the code comments) used to divide by a hardcoded 2 regardless of how many priorities were selected, which penalized a farmer who cared about exactly one thing. Fixed; regression-tested in engine.test.js.

Priority weighting matrix

Base weight is 0.25 per category. Each active priority adds CATEGORY_WEIGHT_BOOST = 0.05 to its mapped category, then the total boost is subtracted back out evenly across all four categories so the weights always sum to exactly 1:

Honesty note 1 — scenario IDs are rank-based, not identity-based. Scenario A is always the do-nothing baseline: repeat the previous crop. Every other candidate crop is scored and then sorted by descending weighted total, and assigned B, C, D… in that order. Under a different set of farmer priorities, "Scenario B" can be a different crop — it is not a fixed label for soybean. The ranking, not the letter, carries the meaning.
Honesty note 2 — the candidate pool is restricted to rice, maize, and soybean (MVP_SCENARIO_CROP_KEYS), matching problem.html's stated MVP scope ("three realistic options"). Honesty note 3 — several coefficients are empirically calibrated, not derived from agronomic literature. They are internally consistent and regression-tested, but they are not independently derived from FAO/agronomic literature the way the crop parameter table (water requirement, pH band, yield) is. These are the first constants to replace with field-validated values once real trial or extension-officer data exists.

6Economics & risk model

Source: computeEconomics() and computeConfidence() in engine.js.

Expected Net Margin/ha = predicted_yield × 1000 × farm_gate_price − variable_cost predicted_yield = base_yield_t_ha × (0.70 + 0.30 × climate_resilience ÷ 100) — a stressed crop under-performs its reference yield.

Risk range

  • Downside fraction = drought_sensitivity × 0.25 (RISK_DROUGHT_DOWNSIDE_MAX) + market_price_volatility × 0.20 (RISK_PRICE_VOL_MAX) + (1−confidence) × 0.15 (RISK_DATA_UNCERTAINTY_MAX).
  • Upside fraction = price-volatility term × 0.60 (RISK_PRICE_VOL_UPSIDE_SHARE) + data-uncertainty term × 0.30 (RISK_DATA_UNCERTAINTY_UPSIDE_SHARE). Drought risk has no upside share — it can only hurt, never help.
  • low = expected × (1 − downside), high = expected × (1 + upside).
  • break_even_price = variable_cost ÷ (predicted_yield × 1000).
  • priceSensitivity(deltaPct) is exposed as a function so the UI can chart margin against a farm-gate price shock of any size.

Confidence model

Starts at 1.0, then:

  • −0.05 if soil chemistry is a static point extraction (always true for this field — SoilGrids).
  • −0.15 if the soil raster's pixel area exceeds 2× the declared field area. SoilGrids' 250 m pixel ≈ 6.25 ha vs. this field's 1 ha default → always triggers here.
  • −0.10 per farmer-input field that fell back to a default (of previous_crop, irrigation_type, priorities, area_ha, capital_available_idr_per_ha).
  • Always appends: "GEOGLAM outlook is a regional (country-level) signal; local field conditions may vary."

Label: score ≥ 0.75 → High; ≥ 0.5 → Medium; else Low.

Worked example — Scenario B (Soybean), default field state

Climate resilience = 82, confidence = 0.80 (High).

Note the counter-intuitive result: Rice's expected margin (13.58M) is actually higher than Soybean's (6.69M) in absolute IDR/ha — Soybean wins on the weighted score (climate resilience, water suitability, soil rotation benefit, and the farmer's stated priorities), not on raw margin alone. This is exactly the "not simply chasing yield or margin" design intent from problem.html — and a reason the margin range must always be shown next to the verdict, not instead of it.

8IoT hardware spec

Full interactive bill of materials, 3D explorer, and diagrams live on iot-3d.html. This section summarizes the numbers that matter for planning, using the corrected figures published there.

Core hardware: ESP32-S3 (dual-core) + Semtech SX1262 LoRa on AS923 (the correct Indonesia/SE-Asia ISM band, not US 915 MHz); two capacitive (FDR) soil-moisture probes at 15 cm and 40 cm; SHT31 air temperature/humidity; 6 V/2 W solar panel with an MPPT/linear charge controller; IP65 enclosure with a single M12 IP68 cable gland. A separately-priced actuation point pairs one 12 V normally-closed solenoid valve, an opto-isolated relay driver, and a Hall-effect flow meter — one actuation point can serve several sensing nodes on the same plot.

Cell self-discharge alone is 5.67 of 16.59 mAh/day — about a third of the total load — and it keeps draining the pack whether or not the node ever wakes up. Omitting it, as iot-3d.html notes, is "the classic way IoT power budgets end up fictional".

Paper autonomy at zero solar input: 4,896 ÷ 16.59 ≈ 295 days. The claimed figure is ≥60 days, not 295 — past roughly two months the binding constraint stops being energy and becomes calendar ageing, connector corrosion, and probe drift. Solar income, de-rated for the wet season (2 W × 1.2 effective peak-sun-hours × 75% charge-path efficiency) is ≈486 mAh/day, a ≈29× recharge margin over the daily load even in the worst monsoon month — the panel is oversized on purpose, to recover the pack after a multi-week overcast run, not merely to balance one day. Energy is not the limiting factor in this design; serviceability is.

9Firmware state machine

iot-3d.html documents the sense/decide/act/verify loop and the per-mode current draws and timings that back Section 8's power budget. This section arranges those same numbers into a fuller lifecycle for firmware implementers — no new current, duration, or event count is introduced here that isn't already in the Section 8 power budget.

1. BootCold/warm start, self-test SDI-12 probes + I²C air sensor, read RTC and last-known state from flash.
2. JoinLoRaWAN OTAA join/re-join. Retries with backoff; repeated failure routes to the offline local-rule path.
3. SleepDeep sleep, RTC timer running. 0.25 mA baseline, 30-min cycle (48 wakes/day).
4. SenseWake, power probes + air sensor, ADC read. 2 s @ 60 mA.
5. EvaluateCompare against crop-stage threshold, rain probability, daily water cap; run the sensor-quality check.
6. TransmitLoRa uplink, +14 dBm AS923. 1.5 s @ 100 mA, then two Class A downlink RX slots (2 s @ 12 mA each).
7. ActuateOnly if Evaluate/downlink calls for irrigation. Relay logic drive, 60 s @ 30 mA per open/close pair.
8. VerifyConfirm real flow via the Hall-effect meter within 30 s; log volume or trip the no-flow alert.
9. FaultEntered from a failed self-test, sensor-quality flag, no-flow alert, or exceeded max runtime. Always resolves toward valve closed.
Offline local-rule path (Section 10's "Offline local rule" guardrail): if Join fails, or the uplink/downlink link is lost beyond N consecutive cycles, the node stops waiting on Transmit/gateway downlinks and runs Evaluate → Act using only its own two probes and a conservative pre-agreed daily water cap. It still passes through Actuate → Verify → Fault exactly as normal, and re-attempts Join on every subsequent wake so it reconnects automatically once the link returns. If local data is itself uncertain, the default is no action — valve stays closed. 
IF soil_moisture < crop_threshold
AND rain_probability_next_6h is low
AND daily_water_limit not exceeded
THEN open valve for N minutes
ELSE send alert / wait

10Safety guardrails

Every guardrail below resolves to the same fail-safe state: irrigation stops and the valve returns to closed (the solenoid valve is normally-closed by construction — de-energised = closed).

GuardrailTrigger conditionSystem responseFail-safe state
Manual override Farmer flips the physical switch or sends an override command. Immediately halts any automatic actuation; surfaces a manual-mode banner in the app. Valve closed until the farmer re-enables auto mode.
Max runtime Valve open longer than the configured cap (e.g. 20 min). Controller force-closes the valve and raises a maintenance alert, regardless of the moisture reading. Valve closed.
No-flow alert Relay commands "open" but the Hall-effect flow meter reports no pulses for > 30 s. Assumes a stuck valve, blocked line, or dry supply; aborts the cycle and flags for inspection. Valve commanded closed, irrigation suspended until acknowledged.
Sensor-quality flag A probe reading is out of physically plausible range, the two probes disagree beyond a threshold, or a reading is stale. Decision engine discards the suspect input, falls back to the last known-good reading, raises a maintenance flag. No new irrigation triggered off a flagged sensor — valve stays/returns closed.
Offline local rule LoRa uplink/downlink lost beyond N cycles. Node reverts to the closed-loop rule entirely locally, using only its own probes and a conservative pre-agreed daily water cap. If local data is also uncertain, default is no action / valve closed.

11Privacy, consent & data governance

Not implemented. There is no backend, database, or aggregation pipeline in the MVP — this section documents the governance model the optional Gov/NGO "needs & intervention map" branch (problem.html, Section 06) must satisfy before it is built, not a running system.

Individual field-level data (crop choice, margin, soil chemistry, telemetry) belongs to the farmer. The core farmer product (field-level decision & action) never requires sharing it with anyone else. The optional support layer only ever sees an aggregated, consent-gated view.

PrincipleRule
Consent modelA farmer's field-level data is included in any Gov/NGO aggregate only after explicit, revocable opt-in. No default inclusion.
Anonymisationfield_id and any farmer identity are stripped before aggregation; only administrative-unit-level (e.g. village) summaries are exposed to the support layer, never a single field's raw record.
Minimum aggregation thresholdAn aggregate bucket (e.g. "villages needing soil-testing support") must contain data from at least k = 5 consenting farmers before it is shown, to prevent re-identification of a single participant in a small bucket.
RetentionRaw per-field Field State and telemetry are retained only as long as needed to serve that farmer's own recommendations, plus one prior season for trend continuity. De-identified aggregates may be retained longer since they carry no individual link.
Purpose limitationAggregated data may be used only for the stated support purposes (soil-testing prioritization, sensor-as-a-service targeting, extension-visit prioritization) — not resold, not used for enforcement, not used to police subsidy eligibility (explicitly out of scope per problem.html).
